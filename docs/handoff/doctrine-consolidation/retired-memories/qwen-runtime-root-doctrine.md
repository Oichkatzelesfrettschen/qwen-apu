Since 2026-09-04 (PR #169) the appliance has one declared runtime root:
`remote/qwen-home.sh` resolves `QWEN_HOME`, defaulting to `.runtime` beside
`remote/`, and every script derives models, state, deployments, toolchains,
the SearXNG instance, the signing key, and results from it. The laptop runs
from its own checkout `~/Github/qwen-apu`; the sync target is that checkout
(`remote/sync-runtime-tree.sh eirikr@qwen-laptop.local:~/Github/qwen-apu`).
The migration ran 2026-09-04: models digest-verified in place, state,
deployments, key, RyzenAdj, sd-cli, and both llama.cpp trees under
`.runtime`; `make purge-legacy` removed every predecessor path and the
`searxng` account; `make doctor` reads `legacy_paths_present=no`. The serving
bundle since 2026-09-04 22:58 PT is `main-7f8f2ed-r1` (server 70aa78bc...,
built on the laptop from `.runtime/opt/llama.cpp` with the router candidate;
the moved build directory's stale CMake cache was set aside as
`build-raven2-vulkan-production.pre-root-<utc>`), tagged
`deploy/main-7f8f2ed-r1`, qualified on router recovery, the whole LAN matrix,
and rollback; `main-e909cfc-r1` (server 5dd86b90...) is the proven
root-compatible rollback target. A bundle's presets carry absolute paths, so
a bundle cut before the migration (`main-f50d631-r1`) is historical only.
Laptop epoch chain: `$S/router-fix/laptop-epoch.sh` and `laptop-rollback.sh`
run over `ssh ... sh -s NAME` (nothing placed on the laptop); the
lan-authenticated router binds the LAN literal, so probe it from the
workstation, never loopback on the laptop.

**Why:** the user found two incompatible SearXNG install doctrines and a
home-directory sprawl with no uninstall, and ruled "self-contained: every byte
checked in or reproducibly generated under one ignored root."

**How to apply:** on the workstation, run gates as
`bwrap --dev-bind / / --unshare-pid --proc /proc --die-with-parent env
PYTHONDONTWRITEBYTECODE=1 ./remote/repository-quality-gates.sh` from the
worktree, with **`QWEN_HOME` unset**. An exported `QWEN_HOME` overrides the
root a fixture builds for itself, and `qwen-image-launch.sh`'s path-containment
check then reads the fixture's own `state/image-parameters.json` as outside the
root: `test-qwen-image-launch` fails 16 checks that pass with the variable
unset, and the same override reproduces on `main`, so it looks like a
pre-existing red gate rather than a harness error. Let each worktree use its
own `.runtime` default. A test that copies a script into a fixture harness must
copy `remote/qwen-home.sh` beside it; a harness for a script whose resolver
verifies whole bundles copies all of `remote/`, since
`check-runtime-tree.sh` refuses a git source clone outright. Known gaps: helper
binaries `build/vulkan-graphics-service-probe` and `build/telemetry-broker`
live beside the tree (rebuild them after a fresh clone or the launch fails
`graphics_latency_probe_unavailable`); `state/image-parameters.json` is
admission output with absolute paths, hand-rewritten to root paths; campaign
output directories directly under `~` are outside the doctor's enumeration;
`make verify` covers sudo policy, manifest, and ratchet only; the SearXNG lock
has versions without artifact hashes; `require_marker` checks schema version
only. The router cancelled-load defect and its repair are in
[[qwen-router-cancelled-load]].
See [[qwen-lan-bringup-and-merge-program]] and [[qwen-appliance-host]].
